案例 01

完成第一次小型代码审查

场景：接手一个模块，先理解职责和风险，再在确认问题后做最小修改。

  1. 在仓库根目录启动并命名会话：pi --name "review auth module"
  2. 用 @ 附加入口文件和测试，先提交只读任务：输出模块职责、调用入口、错误边界、可能缺陷，明确不要修改文件。
  3. 代理工作期间发现范围不对，输入「先不要修改；补查调用方和失败路径。」并按 Enter，作为引导消息送入当前任务。
  4. 结论确认后，输入「根据已确认的问题做最小修改，并运行覆盖该路径的测试。」；代理仍在工作时可按 Alt + Enter 排为后续任务。
  5. 用 Ctrl + O 展开工具结果和 diff，用 /session 查看会话状态。退出后执行 pi -c 继续最近的会话。

进阶

处理持续工作的关键问题：让项目约定稳定生效，控制工具和上下文，在长会话中分支、回溯和交接。

设置、项目信任与上下文

配置是 JSON，项目设置覆盖全局设置。嵌套对象按字段合并，项目只需覆盖要改的键。直接编辑文件，或使用 /settings 配置常见选项。

位置作用域
~/.pi/agent/settings.json全局（所有项目）
.pi/settings.json项目（当前目录）

最小可用配置

大多数时候无需手写设置：启动默认模型和思考等级可以在 /model、/thinking 选择器中按 Ctrl + S 保存，主题在 /settings 里切换。只有要覆盖默认值时才编辑 JSON：

~/.pi/agent/settings.json 
{
  "defaultProvider": "anthropic",
  "defaultModel": "claude-sonnet-4-20250514",
  "defaultThinkingLevel": "medium"
}

/compact 与 /tree 分支摘要

/compact [说明] 立即压缩当前会话，可选说明用于突出要保留的内容：

session 
/compact 保留 API 重设计决策；迁移脚本只是临时草稿。

/tree 切换到其他分支时，Pi 会询问是否概括刚放弃的分支，并把摘要附加到新位置。三个选项依次是：不生成摘要、用默认提示概括、按自定义重点概括。

不丢数据：压缩和分支摘要都不删除原始条目，会话文件中保留完整记录，可以继续用 /tree 回溯。

用 /session 区分两类问题

上下文溢出先看令牌占用与压缩设置；额度或速率限制属于提供商侧，压缩解决不了，应检查认证、计费状态和错误信息。

会话是一棵树

会话保存为 JSONL，按工作目录隔离。每个条目带 id 和 parentId，当前位置是活动叶子节点，因此一次会话天然可以分支。

特性/tree/fork/clone
输出同一会话文件新会话文件新会话文件
视图完整会话树用户消息选择器当前活动分支
典型用途原地探索备选方案从更早的提示开始新会话继续之前先复制当前工作
分支摘要可选无无
  • 选择一条用户消息时，/tree 把叶子节点移到该消息的父节点，并把消息文本放回编辑器，编辑后重新提交即形成新分支。
  • 选择助手、工具或压缩条目时，叶子节点移到该条目，编辑器留空，可以从该位置继续。
  • 选择根用户消息时，叶子节点被重置为一个空对话，并把原始提示放入编辑器。
选择规则：想要备选方案待在一起，用 /tree；想要独立的会话文件，用 /fork 或 /clone。

会话共享

/export [file] 导出为 HTML 或 JSONL；/import <file> 从 JSONL 导入并恢复；/copy 复制最后一条助手消息。权威记录是 JSONL：它保留完整谱系，可以恢复和继续。

只需要别人看时传 HTML，需要别人接着做时传 JSONL。
案例 02

比较两个重构方案后继续长任务

场景：同一个模块有两种重构方向，需要保留完整讨论过程，选定方案后再进入实现。

  1. 用 /name cache-refactor 命名当前会话，提交包含约束、验收标准和现状证据的方案 A 请求。
  2. 方案 A 完成后运行 /tree，选择最初的用户消息。Pi 会把该消息放回编辑器；将方案约束改为方案 B 并重新提交，形成第二条分支。
  3. 方案 B 完成后再次运行 /tree。在同一棵树中对照两个分支，选择要继续的节点；切换时按需要生成分支摘要。
  4. 执行 /clone，把选中的活动分支复制到新的会话文件，在副本中实施修改；如果要从更早的用户提示建立独立会话，则使用 /fork。
  5. 上下文接近上限时执行 /compact 保留选定方案、接口约束、未完成项和测试结果；舍弃被否决方案的实现细节。
  6. 用 /session 核对令牌占用与会话文件，最后用 /export cache-refactor.html 生成只读审阅材料；需要继续执行时保留原始 JSONL 会话。

拓展

基础工作流稳定后，把重复提示、专门流程、工具和界面能力沉淀为可复用资源，并按需接入脚本或其他程序。

提示模板（Prompt Templates）

提示模板是展开为完整提示的 Markdown 片段，在编辑器输入 /文件名 调用。加载位置：

  • 全局：~/.pi/agent/prompts/*.md
  • 项目：.pi/prompts/*.md（信任项目后加载）
  • 包、设置的 prompts 数组，以及可重复的 --prompt-template <path>

位置参数

写法含义
$1、$2按位置取参数
$@ 或 $ARGUMENTS全部参数
${1:-默认值}参数 1 为空时用默认值
${@:-默认值}全部参数为空时用默认值
${@:N} / ${@:N:L}从第 N 个参数开始 / 从第 N 个起取 L 个
.pi/prompts/review.md 
---
description: 审查暂存的改动
argument-hint: "[关注点]"
---
审查暂存改动（`git diff --cached`）。重点检查：
- Bug 与逻辑错误
- 安全问题
- 错误处理缺口
命名规则：模板名取自文件名，review.md 即 /review。description 省略时使用首个非空行；argument-hint 中 <尖括号> 表示必填参数，[方括号] 表示可选参数。prompts/ 的发现不递归，子目录中的模板需要显式加入设置或包清单。

包（Packages）

包把扩展、技能、提示模板和主题打包，通过 npm 或 git 分享。完整的安装维护命令与第三方扩展示例见速查页 · 包管理。

案例 03

把团队代码审查沉淀为复用能力

场景：团队反复执行同一套代码审查，规则逐渐从一段提示词发展为包含脚本、参考资料和强制保护的工作流。

  1. 规则只有一段稳定提示时，先创建 .pi/prompts/review.md。团队成员用 /review 或 /review 安全边界 调用。
  2. 流程需要执行脚本、按需读取检查清单或处理多阶段步骤时，迁到 .pi/skills/code-review/SKILL.md，用 /skill:code-review <关注点> 显式调用。
  3. 规则必须拦截危险工具调用、保护路径或提供自定义 UI 时，增加 .pi/extensions/ 下的 TypeScript 扩展。提示模板和技能只能提供指令，不能替代运行时强制约束。
  4. 需要跨仓库分发时，按 prompts/、skills/、extensions/ 和 themes/ 组织资源，并在 package.json 的 pi 字段中声明入口。先临时试用：pi -e ./team-review
  5. 检查源码和行为后，安装到项目作用域：pi install ./team-review -l，然后 pi config -l。
  6. 一次性审查可接入 Shell 管道并限制为只读工具：git diff --cached | pi -p --tools read,grep,find,ls "按团队审查规则检查这批改动，按严重程度输出问题。"；需要消费完整事件改用 --mode json，需要外部程序持续控制会话用 --mode rpc。
